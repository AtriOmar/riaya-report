\section{Introduction}
This chapter explains how Riaya is built and how it runs. It starts with the architecture: the principles we followed, the split of the code into a web repository and a voice repository, and the path that a phone call takes through the system. It then goes through the technology stack area by area, with what each tool does in Riaya and why we chose it. A set of screenshots follows, covering the public pages, the doctor dashboard, the secretary view and the administrator back-office. The chapter then covers security and access management and the technical problems we met, with the solutions we adopted. It ends with the evaluations behind our main technical choices, namely the geocoding provider, the road-distance step and the voice model, and with the way the platform was tested.

\section{Global System Architecture}\label{sec:architecture}

\subsection{Architectural Principles}
The design follows three common principles: separation of concerns, event-driven communication, and running every part in a container \cite{fowler2002patterns}.

Separation of concerns decided where each piece of logic lives. The web application owns the database and every business rule: booking checks, the best-fit search, plan limits and billing. The voice server owns the long-lived connections: the phone audio, the session with the AI model, the live WebSocket feeds, the WhatsApp sessions and the job workers. A rule is written once, in the web application, and the voice server asks for it over HTTP.

Event-driven communication is used wherever a person waits for something to happen. The voice server pushes each new transcript line and each booking over a WebSocket \cite{fette2011websocket}, so the administrator and the doctor see them without reloading the page. Delayed work, such as cancelling a request that no doctor answered after 10 minutes, is a job in a queue instead of a timer inside a process.

Containerized deployment means that each part runs in its own Docker container \cite{docker2024}, built by the CI pipeline and started the same way on the server every time.

\subsection{Separation into Two Repositories (Web App and Voice Server)}
The code is split into two repositories.

The \textbf{web repository} is a Next.js application \cite{nextjs2024}. It holds the public pages, the doctor, secretary and administrator dashboards, the review page for patients and the test-call page. It also holds the internal API used only by the voice server, authentication with Better Auth, the best-fit search and the place lookup, plan limits and payments, the doctor AI assistant, the producers of background jobs and the Drizzle schema of the PostgreSQL database \cite{postgresql2024, drizzle2024}.

The \textbf{voice repository} is a Node.js server built with Express \cite{express2024}. It receives the Twilio calls \cite{twilio2024}, bridges the phone audio to Gemini Live \cite{gemini2026live}, runs the caller transcriber and the silence watchdog, and exposes the call tools that the AI uses to search and book. It keeps one WhatsApp session per doctor with Baileys \cite{baileys2024} and runs the BullMQ workers \cite{bullmq2024}. It also contains a separate LiveKit agent process, used on the test-call page to try other chains of models.

The voice server has no database connection. Every read and write, from checking whether a caller is blocked to booking an appointment, goes through the web application's API, and the request carries a shared secret in the \texttt{x-internal-secret} header. The calls also go the other way: when a doctor sends an invoice on WhatsApp, the web application asks the voice server to send it, because the WhatsApp sessions live in that process. The two applications also share Redis: the web application adds jobs to the queues, and the workers in the voice server run them.

This split has a cost: each tool call during a phone conversation makes one extra HTTP request to the web application. In return, the business rules exist in a single place, only the web application holds the database credentials, and the voice server can be restarted or redeployed without touching the database or its migrations. A crash in the voice server stops calls but leaves the doctor dashboard working, and the reverse is also true.

\subsection{Technical Architecture Schema (Microservices, Event-Driven)}
Riaya is not a full microservices system \cite{newman2015microservices}. It has two services with clear interfaces, one database owned by the web application, and a Redis instance shared for jobs. \xref{fig:global_arch} shows the users, the edge, the two servers, the data stores and the external services.

\paragraph{An inbound call.} The main flow is a patient calling the Riaya number:
\begin{enumerate}
    \item Twilio receives the call and sends a webhook to the voice server.
    \item The voice server asks the web application whether the number is blocked. A blocked caller is rejected with a busy signal before any AI starts. If the web application does not answer within about 1.5 seconds, the call goes on, so an outage never turns patients away.
    \item In parallel, the voice server creates the call record and finds or creates the person behind the phone number, both through the web API. It answers Twilio with TwiML that opens a media stream WebSocket \cite{twiliomedia2026}, and it starts a two-channel recording of the call.
    \item A session object bridges the phone audio (8~kHz $\mu$-law) and the Gemini Live session. A copy of the caller's audio goes to the caller transcriber, which cuts it into sentences and sends each one to a transcription model through OpenRouter.
    \item When Gemini Live calls a tool, the tool sends a request to the internal API: look up a place with Google Places, search for doctors and free slots (the best-fit search, which asks the Geoapify Route Matrix for road distances), or book. A booking creates a pending appointment, and the web application adds a job that will cancel it if no doctor answers within 10 minutes.
    \item During the call, the voice server pushes every transcript line and every tool call over its \texttt{/dashboard} WebSocket. Each booking also sends an \texttt{appointment\_booked} event on the same feed. The administrator's Live Calls page listens to it, and so does the doctor's calendar, where the new request appears with a sound.
    \item When the call ends, the call record is closed and its events are saved through the web API. Twilio then sends the finished recording to a webhook of the web application, which checks Twilio's signature and copies the audio to Cloudflare R2.
\end{enumerate}

\paragraph{Background jobs.} Three BullMQ queues run on Redis: the 10-minute timeout of a pending request, the review request two hours after a visit, and the daily subscription renewal. The web application produces the jobs and the workers in the voice server consume them. A worker does not hold the business logic: it calls an internal route of the web application to process the job and, for a timeout or a refusal, places the callback through Twilio or sends the WhatsApp fallback.

\paragraph{Web-side services.} Browsers reach the web application through Nginx, which handles TLS and routes requests. The web application is the only service that talks to PostgreSQL. It calls OpenRouter for the doctor AI assistant and the transcription of consultation recordings, creates presigned upload URLs for Cloudflare R2, starts Konnect payments and receives their webhook, and calls Google Places and Geoapify for the best-fit search.

\paragraph{WhatsApp.} Each doctor links a WhatsApp account by scanning a QR code that the voice server streams to the WhatsApp page over a WebSocket. After that, the web application asks the voice server to send each message, and the message leaves from the doctor's own number. The platform account, linked by the administrator, sends the system messages that do not come from a doctor.

\subsection{Web Application: Next.js, React, TypeScript, Tailwind CSS}
The web application is built with Next.js \cite{nextjs2024}, React \cite{react2026} and TypeScript \cite{typescript2026}, and styled with Tailwind CSS \cite{tailwind2024}. Next.js keeps the pages and the API in one project, which suited a single developer, and TypeScript catches many mistakes before the code runs.

\subsection{Typed API and Data Fetching: Zod, OpenAPI, Orval, SWR}
Each API route declares its input and output with Zod \cite{zod2026}. From these schemas we generate an OpenAPI specification \cite{openapi2024} and, with Orval \cite{orval2026}, a typed client with SWR hooks \cite{swr2026}, so a change to a route shows up as a compile error in the pages that use it.

\subsection{Authentication and Email: Better Auth, Nodemailer}
Better Auth \cite{betterauth2024} handles accounts and sessions inside our own application and database, so user data does not go to an outside identity service. Nodemailer \cite{nodemailer2026} sends the sign-up codes and the secretary invitations.

\subsection{AI Services: Gemini Live, OpenRouter, LiveKit}
Patients speak with Gemini Live \cite{gemini2026live}, a speech-to-speech model that listens, calls the booking tools and answers with its own voice. We chose it after the tests described in Section~\ref{subsec:voice-model-evaluation}.

OpenRouter \cite{openrouter2026} gives access to many models through one API. We use it for the doctor's AI assistant and for transcribing consultations and the caller's words. Requests that can contain patient data only go to providers that neither keep nor train on them \cite{openrouterzdr2026}.

LiveKit \cite{livekit2026} runs a separate agent, used only on the test-call page to compare chains of models.

\section{Conclusion}
This chapter described how Riaya is built. The system is split into a web application, which owns the database and the business rules, and a voice server, which handles the phone audio, the live feeds, WhatsApp and the background jobs and reaches the data only through the web application's internal API. We went through the stack area by area, from Next.js and the typed API to Gemini Live, OpenRouter, BullMQ and the deployment on an Ubuntu server, and showed the main screens of the four interfaces. We then covered how the platform protects accounts and medical data and the technical problems we met along the way. The last section gathered the evaluations that led to Google Places, the road-distance polish and Gemini Live, and described how the platform was tested. The general conclusion that follows sums up the work and the next steps.
